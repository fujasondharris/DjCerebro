## M7 Phases 2–5 (2026-07-30), DONE — build verified, EAR NOT YET VERIFIED

**Phase 2 — band-isolated held loop (`src/lib/loop-hold.ts`).** Its OWN 3-band chain (lowshelf 250 / peaking 1000 / highshelf 4000 at `EQ_KILL_DB` −40, mirroring deck.ts) — `fireLoopOverlay` wired straight to `core.master`, so the deck's kills could never band-isolate it. beat mode kills mid+high, melody mode kills low. Capture length is a parameter and HALVES mid-hold (4 bars → 2 → 1 → ½ → 1 beat); `loop-blend.ts`'s `LOOP_CAPTURE_BEATS` is likewise no longer hardcoded (new optional arg, default 16 = byte-identical old behavior).
- **The pitch ride is STEPPED, one constant rate per stage, deliberately.** A buffer source's progress is the *integral* of its playback rate, so a rate varying *within* a stage makes that stage's wall-clock length depend on the ramp shape and the exit stops being sample-accurate. Constant-per-stage keeps every stage a whole number of cycles, and each step lands on a loop boundary — where a DJ nudging a pitch fader would put it anyway. The final stage is pinned to rate 1.0, so the hold hands over in the track's own key (`exitRate`/`exitBpm`).
- **Exit-on-the-1 is enforced, not hoped for:** the total is padded with whole cycles of the shortest stage until it is a whole number of 16-beat phrases. Checked across all **48** combinations of capture (2/4/8 bars) × target (15/30/45/60s) × halvings (0/2/3/4).
- `fireIsolatedLoopHold` schedules ONE pre-started source per stage rather than mutating `loopEnd`/`playbackRate` from a timer — a mutation landing even slightly late plays a whole extra cycle of the old length, which is exactly how the exit stops landing on the "1".

**Phase 3 — contract.** `action:"loop"` is now a first-class brain command (before, `loop_blend` was ONLY a transition kind on a queue command, so a mid-track hold was structurally pad-only). **Cadence budget split by class, with SEPARATE clocks:** stingers keep the rare 120s floor; performance moves (rolls, `loop`, `eq`) get 20s. Separate clocks matter — sharing one timestamp meant one roll silenced airhorns for two minutes and one airhorn silenced every performance move for two minutes. Vocal clips and scratches are in neither class; salsa/bachata suppression re-asserted over the new move. **Sequence chaining is done in code, not hoped for:** the app books the return consult itself, 18s before the hold's own measured exit.

  - **salsa / bachata:** hard suppression, extended beyond fx — no fx/scratch mid-track, AND no echo_out, no cut mid-phrase, no beatmatched blend into the next track either. Let the track end cleanly, plain gap, then queue the next (dancers need unbroken rhythm and a clear boundary to swap partners). Only an explicit vibe-note request overrides, and El Cerebro says so honestly when it does (it's atypical for this lane).
  - **trance / big-room (Tiesto/Oakenfold-era):** riser is the native tool, fired only in the last bars before a queued transition (via `remainingSeconds`); siren and rewind are explicit AVOIDs here (off-genre — dub-siren/pull-up culture doesn't belong at a trance set); airhorn is rare and vibe-note-only. Long blends (16-32+ bars) are the norm here, the mirror image of the Latin lane's short cuts.
  - **rewind:** crowd-earned, never scheduled — only on an explicit vibe-note request or right after a human-rated 👍 transition. **brake:** quick punctuation right before a "cut", sparingly. **tag:** intros/hand-offs, at most once every few tracks, and it's fine if it silently doesn't fire (see the fx.ts note above).
  - **Genre-uncertain fail-safe:** BPM alone isn't enough (bachata ~120-140 BPM overlaps house/trance) — if the track name doesn't make the genre clear, skip airhorn/siren/rewind entirely rather than risk firing one into what might be a salsa/bachata track.
  - **Frequency cap:** at most one fx of any kind per ~10 minutes — check `fxLastSecondsAgo`, and if under ~600s with no explicit request, choose `"none"` instead. Never two fx back-to-back without a queue/tempo_nudge action between. Never fire fx while a queue transition is currently in progress — let it resolve first.
  - **Fx-as-energy-rescue:** legitimate at a low point in the set (siren = "something's coming") but ONLY paired with an immediate queue/track change in the same or next command — never a standalone stinger into a lull with nothing following it.

## Lazy-crate re-architecture for large libraries (2026-07-26)

**Why:** Jason's real crate is ~264-286 mp3s (~1.8GB, confirmed live against the real "DJ Supermercado Crate" Drive folder while building this — 286 tracks today). The old design ("Load crate from Drive" = full-download every playable file into an in-memory `File`, right there in React state) took 5-15 minutes and would crash iOS Safari on memory well before finishing. Re-architected around three ideas: metadata-only crate loading (parse tags from a partial fetch, never the whole file), on-demand full-file download only when a track is actually queued/loaded, and an IndexedDB cache so downloaded files (and the crate's metadata list) survive a reload at the party.

- **Partial-fetch tag parsing, `src/lib/crate-lazy.ts` (new) + `src/app/api/crate/[id]/route.ts`:** the ID3v2 tag (BPM/key text frames, and the Serato BeatGrid GEOB frame inside it) lives at the START of an mp3, and the ID3v2 header declares its own total size in bytes 6-9 (a syncsafe int) — `readId3DeclaredHeaderSize()` reads that declared size; `fetchTagHeader()` fetches the first 256KB via a Range request, and if the declared size exceeds what was fetched (a rare "monster header," e.g. embedded cover art), re-fetches exactly the declared size in one more round trip rather than guessing. The proxy route now forwards a client `Range` header to BOTH Drive paths (googleapis `alt=media` and the keyless `drive.google.com/uc`) and passes the upstream's real status (206 partial / 200 whole) and `Content-Range`/`Content-Length` straight through (`buildUpstreamRangeHeaders()`/`buildProxyResponseHeaders()` in `src/lib/crate.ts`, pure, checked in `scripts/check-crate-route.mjs`) — a plain full-file download (no Range) behaves exactly as before. **id3.ts/serato.ts were NOT touched** (out of scope, per every prior milestone) — the fetched header bytes are wrapped in `new File([bytes], name)` and handed to the existing `parseId3Tags()`/`parseSeratoBeatgrid()` unmodified, the same "wrap a Blob as a File" trick `page.tsx` already used elsewhere (`loadFromBlob()`).
- **Metadata-first crate entries, `src/app/page.tsx`'s `CrateTrack`:** `{id, name, size, bpm, key, grid, source: "drive" | "local", file?: File}` — Drive entries carry NO `File`/blob at all; local file-picker entries keep their in-memory `File` exactly as before (unchanged behavior — they never needed a network round trip, and can't survive a reload either way). **Bug fixed in the same pass:** the pre-existing Drive-add path generated a fresh random id (`makeTrackId(track.name)`) for every added track, discarding the real Drive file id once the (then-mandatory) full download finished — harmless under the old full-download design, but fatal for lazy loading, since a later on-demand download needs that real id to re-fetch `/api/crate/[id]`. Drive entries now use the real Drive file id (`track.id` from the listing) as the crate entry's id. "Load crate from Drive" now = list (unchanged) + a bounded-concurrency (~4 at a time) tag-header-only fetch per playable track (`handleAddAllFromDrive()`, via the new `runWithConcurrency()` in `src/lib/concurrency.ts`), showing "Reading tags X/N…" via `driveTagProgress` state so the UI stays responsive across a 200+ track crate. A repeat click replaces the crate's Drive-sourced entries (refresh, not duplicate) — local entries untouched.
- **On-demand download + IndexedDB cache, `src/lib/track-cache.ts` (new):** `getTrackBlob(id, fetchFull, opts)` — an IDB hit bumps recency and returns the cached `Blob`; a miss calls `fetchFull()` (the proxy, no Range — the whole file), stores `{id, blob, size, lastUsed}`, and evicts per a pure LRU planner (`planEvictions()`) before writing. **Cache caps: ~60 files OR ~500MB, whichever hits first**, evicting least-recently-used — a deliberately conservative slice of iOS Safari's real-world IndexedDB ceiling (roughly ~1GB per FACTS), leaving headroom for the ~2MB SFX/vocal-clip cache and whatever else Safari counts against the same origin quota. Zero deps, raw IndexedDB (`createIndexedDbStore()`); the open() promise resets itself on failure rather than permanently caching a rejection, so a transient open failure doesn't wall off the cache for the rest of the session. `page.tsx`'s `getTrackForPlayback(track)` is the one choke point deck loading AND the autopilot queue both go through: local entries resolve their in-memory `File` directly (no network); Drive entries go through `getTrackBlob()`, logging an honest `"downloading <name>…"` brain-log line only on a real cache miss (`onCacheMiss`, fired before the network call starts). `useDeckController`'s `loadFile()` widened from `File` to `File | Blob` (page.tsx-local hook, not `Deck` itself) so a cached/downloaded Blob never needs to round-trip back through a `File` wrapper.
- **Crate-list persistence, `src/lib/crate-store.ts` (new, localStorage, same guard-and-no-op pattern as `history-store.ts`/`cost-store.ts`):** Drive-sourced crate metadata (never a File blob) is saved on every crate change and restored on mount, logging `"Crate restored (N tracks)"` via the existing brain-log UI — a reload at the party doesn't lose the crate. Local file-picker entries are deliberately excluded (can't survive a reload anyway; unchanged behavior). Cache-hit state (`cachedIds`, which tracks are actually downloaded) is hydrated separately from IndexedDB on mount so the crate list's "•" party-safe marker is accurate immediately, not just after the first queue/tap.
- **Wifi-dies behavior (the actual point of this milestone):** a track that's already been downloaded once (played, prefetched, or restored-and-previously-cached) keeps playing/queuing fine with no network at all — IndexedDB doesn't care that wifi is gone. A track that was NEVER downloaded and gets queued while offline fails at the `getTrackForPlayback()` step inside `executeQueueCommand`/`handleCrateTap`; that failure is wired into the EXACT SAME guard-reset-and-log path as the pre-existing "track not found"/"could not decode" failures (clears `askedForTrackRef`, logs an honest `queue: could not download "<name>" (...)"` line) — autopilot's existing failure ladder (one retry after 10s, then autopilot turns itself off with a log line) applies unchanged, verified by reading `executeQueueCommand` before adding the new step rather than assuming.
- **UI additions, `src/app/page.tsx`'s `CratePanel`:** a "•" prefix on any crate-list item that's party-safe (local entries always; Drive entries once cached) — computed from a `cachedIds` Set, not stored redundantly on each entry, so there's one source of truth. A "Prefetch next 10" button (nice-to-have, kept simple) downloads up to 10 not-yet-cached Drive tracks via the same `getTrackForPlayback()`/bounded-concurrency machinery, for pre-party warm-up.
- **FX/vocal-clip warm-up (scope addendum, mid-task):** `FxPlayer`/`VocalPlayer` (`src/lib/fx.ts`/`src/lib/vocal.ts`) each lazy-load a clip only on its FIRST fire — if wifi died before that first use, the clip was dead for the rest of the set, even though the total asset weight is tiny (~2MB: 7 stingers + 32 vocal clips). Both gained an additive `preloadAll()` method (the one sanctioned exception to "don't touch fx.ts/vocal.ts" for this milestone — additive only, existing `play()`/`playCategory()` on-demand paths are unchanged) that eagerly fetches+decodes every known clip via the SAME `load()` those paths already use, bounded concurrency via the same `runWithConcurrency()`. `page.tsx`'s `handleWarmUpFx()` fires automatically (fire-and-forget, non-blocking) when autopilot is toggled ON, plus a manual "Warm up FX" button in `FxPanel` for pre-party use before autopilot is even started — one brain-log line on completion (`"FX warmed: N clip(s) ready"`), another if anything failed.
- **New checks:** `npm run check:crate-lazy` (`scripts/check-crate-lazy.mjs` — ID3-declared-header-size math incl. a synthetic "monster header," `fetchTagHeader`'s grow-if-bigger logic against a mock `RangeFetcher`, plus a sanity pass against the real committed `test-120bpm.mp3` fixture), `npm run check:track-cache` (`scripts/check-track-cache.mjs` — `planEvictions`' pure LRU policy: under-cap, file-count cap, byte cap, incoming-never-evicted; `getTrackBlob`'s cache-hit/miss/eviction/IDB-unavailable-fallback behavior against a plain `Map` standing in for IndexedDB, since Node has no real IndexedDB), `npm run check:concurrency` (`scripts/check-concurrency.mjs` — ordering preserved despite out-of-order completion, bounded in-flight count, `onItemDone` fires in completion order, edge cases). `scripts/check-crate-route.mjs` extended (not replaced) with `buildUpstreamRangeHeaders()`/`buildProxyResponseHeaders()` cases.
- **Verification:** `npm run build`/`npm run lint` clean. All 18 `check:*` scripts green (15 pre-existing + 3 new) EXCEPT the two pre-existing `check:serato` assertions against Jason's real files in `Downloads\` (recon data, not committed fixtures) — confirmed via `git stash` that these two fail identically on the pre-this-milestone commit too (a float-precision/real-file-drift flake unrelated to this work, not introduced or worsened here). **Live-verified against the real production Drive folder** (dev server, real `GOOGLE_API_KEY`, real `DJ_PASSCODE` cookie): `GET /api/crate` → 286 real tracks, `source: "live"`; `GET /api/crate/<realId>` with `Range: bytes=0-1023` → real `206 Partial Content`, `Content-Range: bytes 0-1023/7550292`, exactly 1024 bytes received; the same id with NO Range header → real `200`, exactly 7550292 bytes (whole-file path confirmed unchanged).

## Suggested cue points (synced lyrics -> pre-placed cues), 2026-07-26

Builds on the cue-point system above: instead of every cue starting from a blank rehearsal MARK, a rerunnable pipeline pre-populates each crate track's cue list with candidate call-response/ad-lib moments pulled from lrclib.net's synced lyrics — rehearse mode becomes "assign and nudge" instead of "hunt and mark" for any track lrclib has covered.

- **`scripts/suggest-cues.mjs` + `npm run suggest:cues`:** fetches the live crate listing (same precedence as `src/app/api/crate/route.ts` — real `GOOGLE_API_KEY` first, the committed `src/data/crate-manifest.json` fallback second, a friendly exit-0 notice if neither is available), reads `GOOGLE_API_KEY`/`GOOGLE_DRIVE_FOLDER_ID` from `.env.local` via a tiny hand-rolled parser written into this script (values are read into `process.env` and never logged — this is a standalone Node script, not the Next app, so it doesn't get `.env.local` for free), then for each playable (mp3) track: cleans the messy YouTube-derived filename, tries multiple `{artist, title}` query variants against lrclib's `/api/search`, and — where synced lyrics are found — extracts up to ~6 candidate cues (parenthetical ad-lib lines + repeated coro lines, spread across the song, skipping the first 10s). Writes `src/data/cue-suggestions.json` (`Record<cueTrackKey, {name, matchedTitle, matchedArtist, source:"lrclib", cues:[{atSeconds,label}]}>`, keys sorted for a low-noise diff across reruns). lrclib responses are cached in `.cache/lrclib/` (new, gitignored) keyed by request URL, so a rerun after adding new crate tracks only hits the network for tracks it hasn't asked about before — rate-limit friendly by design (sequential, one request in flight at a time, a small delay between real network calls only, and a descriptive `User-Agent` header, all per lrclib's own etiquette).
- **Pure logic, `src/lib/lyrics-match.ts` (new):** name cleaning (`cleanTrackName`) strips known downloader noise ("(Official Video)", "(Video Oficial)", "(Audio)", "(Letra)", etc. — deliberately NOT "(Remix)", which is real title information), truncates anything after a top-level "|" (normalizing the fullwidth "｜"/"⧸" some uploaders use first), collapses a duplicated-or-extended leading artist segment ("Yandel - Yandel - Plakito" and "Zion & Lennox - Zion & Lennox Ft Yandel & Farruko - ..." both collapse the same way), then splits on the LAST " - " boundary. `buildQueryVariants()` generates fallback guesses off that (feat.-stripped artist, last-segment-only artist for an uploader-prefixed name, a blunt bracket-stripped title, and a combined-query null-artist fallback) — verified against real names copied verbatim from the live 286-track crate (`scripts/check-lyrics-match.mjs`, `npm run check:lyrics-match`, new), not invented "clean" examples. `titleSimilarity()`/`pickBestMatch()` verify a candidate against a target duration when the caller has one (per the dispatch's FACTS — duration verification wins over title similarity) or fall back to a Dice-coefficient title-similarity threshold otherwise; **this script never actually supplies a duration** (the crate listing doesn't carry audio duration without downloading the whole file, out of scope here — same "no id3/serato touch" boundary every prior milestone respected), so every real match in the committed output went through the similarity-only path — `pickBestMatch`'s duration-aware branch is real, correct, unit-checked code, just not yet exercised by the live script. `parseSyncedLyrics()`/`extractCallResponseCues()` turn an lrclib `"[mm:ss.xx] line"` blob into candidate cues (mostly-parenthetical lines, or lines that repeat elsewhere in the same lyrics — a coro the crowd answers), bucket-spread across the song's span when there are more than the ~6 cap.

## Deferred-action mechanism + cost-reduction pass (2026-07-26)

Found at soundcheck: owner chats "do 30 seconds then transition into the next song" → brain replies with a one-command ack (`action:"none"` + `say`) → nothing ever re-invokes it 30s later → the set just keeps playing, silently ignoring the instruction. Root cause: the brain returns exactly one immediate command and was never given a way to ask for a callback. Landed together with a live-measured cost blowout (a real call with the full 326-track crate = 41,191 input tokens = $0.083/call, ~90% of it the crate listing) and a review-panel loophole in the cooldown classification — all three folded into one pass since they touch the same request/response contract.

- **Deferred re-consult, `src/lib/brain.ts` + `src/app/page.tsx`:** every `CommandSchema` variant (queue/tempo_nudge/fx/eq/none) gains optional `followUpSeconds: z.number().min(5).max(600)` — "re-consult me in N seconds." `SYSTEM_PROMPT` gained a tight rule: the brain can't schedule a future action inside one command, so a timed instruction gets acknowledged in `say` AND `followUpSeconds` set; the deferred re-consult call still sees the instruction via `lastVibeNote` (with its age) plus the live position. **Real bug found via the SDK's own `zodOutputFormat()`, not caught by any unit check:** the first pass reused ONE `z.number().min(5).max(600).optional()` *instance* across all 5 schema variants — Zod's `toJSONSchema()` deduped the repeated object into a top-level `$defs` entry with `$ref` pointers per variant, and Anthropic's structured-output endpoint flatly rejects `$defs` under `anyOf` (`400 output_config.format.schema: For 'anyOf', '$defs' is not supported` — reproduced live against the real API with a real key, not guessed). Fixed by making it a factory (`followUpSecondsField()`, called fresh at each of the 5 call sites) so every occurrence serializes inline — re-verified against the live API afterward (see Verification below). **Lesson for future schema edits:** never share a zod schema *instance* across discriminated-union branches meant for `output_config.format` — always a factory function, even though nothing in the unit checks (which only exercise `CommandSchema.safeParse`, never the JSON-Schema serialization) would catch the difference.
- **`page.tsx`'s scheduling:** a single pending-follow-up slot (`followUpTimeoutRef`/`followUpRetryTimeoutRef`) — a new user chat, a new `followUpSeconds` from a later response, or toggling autopilot off all cancel it (latest-wins). The scheduled call fires with `message: null` (the standing `lastVibeNote` carries the instruction), respects `brainBusy` (one retry ~2s later, then drops with a log line), and works with autopilot ON or OFF — this is the mechanism that makes a manual-mode timed test actually fire.
- **`consultReason` on `DjState` (`"user_chat" | "autopilot_poll" | "follow_up" | "opener"`):** wired honestly at all four real call sites (`handleChatSubmit`, the two autopilot-poll branches, `fireFollowUp`) so the brain knows WHY it's being asked — `SYSTEM_PROMPT` explains the field, `follow_up` meaning "you asked to be re-consulted, act on the deferred instruction if its moment has come."
- **Two adversarial-review fixes to the fx cooldown floor, both closing real loopholes, neither caught by the original design:** (1) the floor originally keyed off "this call's `message` was null" — but a deferred follow-up's message is ALSO null (the instruction rides in `lastVibeNote` instead), so an explicitly human-requested fx ("hit an airhorn in 30 seconds") could get silently suppressed by the autopilot floor. Fixed via `isHumanInitiated(reason)` (pure, `src/lib/brain.ts`) classifying by `consultReason` instead of message-nullness. (2) a follow-up SCHEDULED FROM an autopilot-originated call (opener/autopilot_poll sets `followUpSeconds`) would report its own wire `consultReason` as `"follow_up"` on re-consult — which `isHumanInitiated` treats as exempt — letting an autonomous chain borrow the human exemption. Fixed by tracking the follow-up chain's ROOT reason (`followUpRootReasonRef`, set once at the first hop, inherited unchanged across an arbitrarily long chain) and classifying the cooldown by the root, not the wire value — `resolveCooldownReason(wireReason, rootReason)` (pure, tested for all 4×2 combinations incl. a lost-root fail-closed case). The wire `consultReason` sent to the brain stays honestly `"follow_up"` either way; only the LOCAL cooldown classification uses the resolved root.
- **Prompt caching, `src/app/api/dj/route.ts` + `src/lib/brain.ts`'s `buildSystemBlocks()`:** `SYSTEM_PROMPT` (several K tokens of stable rulebook) now goes over the wire as `system: [{type:"text", text: SYSTEM_PROMPT, cache_control:{type:"ephemeral", ttl:"1h"}}]` instead of a bare string — verified via the `claude-api` skill against `shared/prompt-caching.md`'s live pricing table (1h TTL: write 2x, read 0.1x; the app's call cadence — one call every few minutes with occasional gaps — makes 1h strictly better than the 5m default). `src/lib/pricing.ts`'s `CACHE_WRITE_MULTIPLIER` updated from 1.25 (5m) to 2 (1h) to bill this honestly. **Verified live, cold-then-warm:** first call `cache_creation.ephemeral_1h_input_tokens: 7197`, cost $0.0295; second call `cache_read_input_tokens: 7197`, cost $0.0022 — real cache hit, not assumed.
- **Compact crate + candidate windowing (the ~90%-of-tokens fix), `src/lib/brain.ts`:** `CompactCrateEntry {n, t, bpm?, k?, g?}` replaces the old `{id, name, bpm, key, hasGrid}` wire shape — `n` is a per-call index (position in the full stable-ordered crate list, resolved back to the real Drive id via `page.tsx`'s `crateIndexMapRef`, rebuilt every call), `t` is a cleaned display name (`src/lib/lyrics-match.ts`'s `cleanTrackName()`, payload-only — the UI's own display name is untouched), null/false fields omitted rather than sent explicitly. `QueueCommand.trackId` is now the STRING FORM of `n`, not a real crate id — schema shape unchanged (`z.string().min(1)`), only its semantics changed. `buildCrateWindow()` (pure): when nothing is live, sends the FULL compact list (an opener needs the whole crate, and it's one call — also the only shape byte-stable enough to cache). When something IS live, sends only BPM-compatible candidates (±10%, including half/double-time via the same multiplier logic as `beatmatch.ts`'s `syncTempo()`) + anything the current vibe note name-matches + a random wildcard sample (default 25, injectable `random` for deterministic tests), capped at ~100 entries total. `SYSTEM_PROMPT` discloses the windowing honestly (the full crate still exists, the brain just isn't always shown all of it) and explains the compact field mapping.
- **Crate-block caching interaction, decided honestly (not left ambiguous):** `buildRequestBlocks()` (replaces the old single-string `buildUserMessage`) sends the user message as TWO content blocks — `[crate block (cache_control 1h TTL, ONLY when `crateCacheable`), volatile block (state/note/lessons, never cached)]`. `crateCacheable` is `!windowed` from `buildCrateWindow()` — the full opener-call list is stable and cache-eligible; a windowed per-call slice changes every call (the live BPM moves, the wildcard sample re-rolls) and would only pay the 2x write premium with zero read reuse, so it's deliberately sent uncached. ## Craft pass #2 — vocal-clash transitions, phrase-aligned firing, Camelot mixing, set-arc/anthem residency, tempo-gap rule (2026-07-28)

Five craft rules layered onto the mix-in/mix-out + lesson-ledger foundation from the section above: per-track vocal maps (derived from the same synced-lyrics pipeline as the cue suggestions) drive vocal-clash-aware transitions, transitions now fire on the live track's own next 16-beat phrase boundary instead of the instant the brain replies, TKEY is normalized to Camelot notation for real harmonic-mixing rules, a party-length selector feeds set-arc/anthem-vs-filler residency guidance, and a hard BPM-gap threshold forces cut/echo_out over a smeared blend.

- **Part 1 — vocal maps, `scripts/build-vocal-maps.mjs` (new) + `src/lib/vocal-map.ts` (new):** the build script reuses `suggest-cues.mjs`'s exact crate-listing/name-cleaning/matching/`.cache/lrclib/` plumbing (same GOOGLE_API_KEY-first/manifest-fallback precedence, same lrclib cache — a rerun after `suggest:cues` has already fetched a track costs zero network calls, since both scripts build the identical lrclib URLs) but derives intervals from the FULL synced-lyrics line list (not just `suggest-cues.mjs`'s small call-response subset) via `vocal-map.ts`'s pure `buildVocalIntervalsFromLines()`: each non-blank line spans `[line.time, next line.time)` capped at +8s, spans separated by <3s merge into one continuous interval, boundaries round to 0.1s (via a scale-then-round trick — dividing by 0.1 directly produced float artifacts like `4.6000000000000005`, fixed before committing). Output `src/data/vocal-maps.json`, keyed identically to `cue-suggestions.json` (`cueTrackKey()`, verified by reading `cue-store.ts` before assuming). **Real run against the live 326-track crate:** 318/326 matched (98%, matches the dispatch's pinned FACTS estimate exactly), 525 intervals total, committed.
- **`src/lib/vocal-map.ts`'s other pure exports:** `getVocalIntervals`/`hasVocalMap` (lookup), `isVocalActive`/`firstVocalAfter`/`activeVocalEndsAt` (point queries), `vocalGaps(intervals, minGapSeconds)` (instrumental gaps incl. the pre-first-vocal intro gap — filtered by `minGapSeconds` like any mid-song gap — and the post-last-vocal outro gap, whose true end is unknown so it's `Infinity`, always satisfying any threshold), `nextGapAtOrAfter` (the next not-yet-passed gap from an already-computed list), and `pickTransitionStart(candidates, blendSeconds, liveIntervals, liveOffsetSeconds, incomingIntervals, incomingStartSeconds)` — for each candidate delay, clips both tracks' vocal intervals into the shared local `[0, blendSeconds)` window (the LIVE window shifts by the candidate delay since the live track keeps playing; the INCOMING window is fixed to the incoming track's own timeline regardless of which candidate fires, since it always starts fresh at `incomingStartSeconds` — this is the load-bearing subtlety a first draft of the check script got wrong before being corrected, see the file's own doc comment), sums the overlap, and picks the minimum (ties → earliest, via a strict `<` comparison over ascending-ordered candidates).
- **Brain payload (`src/lib/brain.ts`):** `CompactCrateEntry` gains `firstVocalSeconds?: number` (rounded whole seconds, omitted when no vocal map); `buildCompactCrateEntry()` gains a 6th optional param for it (backward compatible — every pre-existing call site with 5 args still compiles and omits the field). `DjLiveState` gains `vocalActiveNow?: boolean`, `nextVocalGap?: {start, end: number|null} | null`, `vocalEndsAt?: number | null` — all THREE fields are `undefined` (omitted, never `false`/`null`) together when the live track has no vocal map at all, so "unknown" stays distinct from "confirmed instrumental" (per the dispatch); when a map exists they're always real values. `page.tsx`'s `deckLiveState()` now takes an optional `cueKey` param (the same stable per-track key `vocal-maps.json` is keyed by — resolved via a new `cueKeyForLabel(label)` helper reading the existing `cueKeyARef`/`cueKeyBRef`) to do the lookup.
- **`SYSTEM_PROMPT` vocal-clash rule:** never let two vocal sections run simultaneously in a blend; the brain doesn't control the exact blend TIMING (the engine phrase-aligns it, see Part 2) but does choose transition kind/durationBars, so it's told to favor a short blend/cut when `vocalActiveNow` is true and prefer a longer blend when `nextVocalGap` signals an instrumental window is coming; time the exit so the incoming vocal enters as the outgoing one ends (`vocalEndsAt`); prefer firing inside the outgoing track's own instrumental gaps; alternate vocal INTENSITY (rap/spoken vs. belting, inferred from genre/name) across consecutive queues as a palate-cleanser.

- **Part 2 — phrase-aligned firing, `src/lib/phrase.ts` (new):** `nextPhraseBoundaries(grid, positionSeconds, tempo, count, fallbackBpm?)` — pure, no timers — returns the next N phrase-boundary positions (`anchor + n*16 beats`, same `PHRASE_BEATS` convention `energy.ts` already established) as OUTPUT-time delays-from-now (`(boundarySourceSeconds - positionSeconds) / tempo`, the same source→output conversion `deckLiveState().remainingSeconds` already uses). A `null` grid falls back to an anchor-0 estimated grid built from `fallbackBpm` (same "estimated grid" convention `page.tsx`'s own `effectiveGrid()` uses elsewhere); with neither a real grid nor a fallback BPM, or a non-finite/non-positive tempo/bpm/count, it returns `[]` rather than fabricating a beat.
- **`page.tsx`'s `executeQueueCommand`:** the whole `runTransition()` call (plus its `onGain`/`onDone` closures) was factored into a `fireTransition()` closure so it can fire either immediately or from a delayed `setTimeout` — `outPositionSeconds` (the ledger tie-in) is captured INSIDE that closure specifically so a delayed fire records the position at the actual fire moment, not the command-arrival moment, per the dispatch. `"gap"` is unchanged (it already waits for the outgoing track's natural end via `onEnded`, so `fireTransition()` is called immediately — it just arms the listener). Every other kind computes up to 4 phrase boundaries within a 16-second output-time cap (`nextPhraseBoundaries(...).filter(d => d <= 16)`); an empty result (no bpm/grid at all, OR the live track's own phrase interval is longer than the 16s cap — a deliberate extension of the dispatch's "no boundary computable" fallback, documented in-file) fires immediately, unchanged from pre-this-pass behavior. - **Autopilot margin bump:** `AUTOPILOT_REMAINING_THRESHOLD_SECONDS` 45 → 60 — a phrase wait can now delay a transition's actual start by up to the 16s cap past the brain's response, so the early-consult margin needed enough headroom that a wait never pushes a transition past the live track's own mix-out point into a dead outro. Applies to both the `remainingSeconds` and `mixOutSeconds`-distance triggers (they share the one constant).
- **`SYSTEM_PROMPT` phrase-aligned-firing note:** purely informational — the brain doesn't set any new field; it's told the engine times the actual start automatically (within ~16s), so its `say` shouldn't assume instantaneous execution.

- **Part 3 — Camelot harmonic mixing, `src/lib/camelot.ts` (new):** `toCamelot(raw)` — pure, zero-dep — pass-through-normalizes already-Camelot input (`"8a"` → `"8A"`, confirmed some of Jason's real tagged files already use this, per the M2 fixtures' TKEY=8A/11A) or converts musical-key notation (`"Am"`, `"C#m"`, `"Dbm"`, spelled-out `"A minor"`, etc. — TKEY's own ID3v2 spec allows note+accidental+optional trailing "m") via a hardcoded standard Camelot-wheel lookup table (12 pitch classes × major/minor, cross-checked against the well-known 8A=Am/8B=C anchor and several other known pairs before committing), including rarer enharmonic spellings (`Cb`=B, `Fb`=E, `E#`=F, `B#`=C). Unparseable/absent input (TKEY's own `"o"` off-key marker, garbage text, empty/null) → `null`, never a raw string the brain's Camelot rules can't interpret. **`page.tsx` applies this at the two call sites** (`buildFullCompactCrate()`'s `k` field, `deckLiveState()`'s `key` field) — `brain.ts`'s `buildCompactCrateEntry()` itself does NOT convert (its doc comment states the `key` param must already be Camelot notation), keeping the conversion boundary at the one place raw TKEY text enters the payload.
- **`SYSTEM_PROMPT` Camelot rule:** prefer the same code, ±1 on the wheel, or the relative major/minor (same number, other letter); a deliberate +2 is a real energy-lift move, not a mistake; an incompatible key under a BLEND clashes audibly — use "cut"/"echo_out" at a phrase boundary instead of forcing a long melodic blend; key rules matter most for the sustained blend kinds and matter little for "cut"/"gap" (no overlap); never sacrifice energy/genre fit purely to chase a better key match — it's a tiebreaker, not a veto.

- **Part 4 — set arc + anthem residency, `src/lib/party-store.ts` (new) + `src/app/page.tsx`:** `DjState` gains `partyElapsedSeconds` (seconds since autopilot was FIRST turned on this party) and `partyPlannedSeconds: number | null` (the human-selected length). **Persistence design choice, documented per the dispatch's "your call":** the party START timestamp persists to `localStorage` (`djsm.party-start-ms`, same guard-and-no-op pattern as every other `*-store.ts`) so a reload mid-party doesn't reset the elapsed clock — and there's deliberately NO reset control in this pass (not requested): toggling autopilot off and back on again does NOT restamp it, matching "since autopilot first turned on this session" read literally; a real reset needs a future control or a manual `localStorage` clear. `partyPlannedSeconds` also persists (`djsm.party-planned-seconds`) and is mirrored into a ref (`partyPlannedSecondsRef`) alongside its React state, since `buildDjState()` can be read from the autopilot poll's long-lived `setInterval` closure — the same staleness concern every other `*Ref` mirror in this file already guards against.
- **UI:** a small party-length `<select>` (Off/1h/2h/3h/4h, `PARTY_LENGTH_OPTIONS`) next to the "Start autopilot" button in `BrainPanel`'s header row — reuses the existing `cueSelect` CSS class verbatim, no new CSS needed.
- **`SYSTEM_PROMPT` set-arc rule:** warmup → build → the night's biggest moment around ~62% of `partyPlannedSeconds` when a length is set (unset means judge the arc qualitatively off `partyElapsedSeconds` and the room instead of a hard percentage) → ride the momentum → a controlled cooldown, plus deliberate "breathe" valleys right after a peak. **The residency-vs-anthem tension is resolved explicitly** (extending the existing Residency bullet from the mix-in/mix-out pass): a plain filler/energy-maintenance track still gets the ~90-180s quick-mix treatment, but a genuine crowd anthem or banger (judged from owner ratings/ledger notes plus general knowledge of the track name/artist) earns its FULL arc instead — ride it to roughly its own ~60% climax before planning the exit, don't rob the payoff by cutting it at the generic filler window. The prompt is explicit that the anthem's own ~60% and the SET's own ~62% are related but distinct decisions.
